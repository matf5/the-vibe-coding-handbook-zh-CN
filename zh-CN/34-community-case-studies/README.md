## 🎯 为什么案例研究重要

氛围编程处于两个极端之间：炒作（"AI 能构建一切"）与恐惧（"AI 写不安全的代码"）。两者都不完整。真实项目处在中间——它们交付得很快，它们会出问题，团队通过复盘所发生的事来学习。

本节收集来自社区的、匿名的真实世界案例研究。每个案例遵循相同的结构：**构建了什么、如何使用 AI、哪些做对了、哪些做错了，以及学到了什么。**

> 请用本章末尾的模板投稿你自己的故事。社区投稿的案例研究是第六阶段的核心。

## ✅ 成功故事：个人开发者一个周末交付 MVP

**项目：** 一个本地健走小组网站，用于列出健走活动、记录出勤并分享照片。

**AI 如何使用：** 开发者（不是程序员）用 Replit Agent 根据自然语言描述生成了全栈应用，然后用 Cursor + Claude Sonnet 5.5 优化 UI 并修复 Bug。

**做对了什么：**
- 零编程经验，约 8 小时做出可用的 MVP
- 身份验证、数据库与照片上传全部生成并接通
- 当天通过平台的一键托管完成部署

**做错了什么：**
- 被问到时，开发者无法解释身份验证如何工作
- 没有写测试；一个日期处理 Bug 导致出勤记录重复
- 在与小组成员分享链接之前没有运行安全扫描

**学到的经验：**
- 快速交付，但在邀请真实用户之前先加测试
- 对任何处理个人数据的东西都运行安全扫描
- 让智能体解释关键逻辑，直到你理解它为止

**结果：** 网站已面向 50 多名小组成员上线；开发者现在正逐段学习阅读生成的代码。

## ✅ 成功故事：专业团队大规模采用智能体

**项目：** 一个中型电商平台，把旧版结账逻辑迁移到新服务。

**AI 如何使用：** 工程团队用 Claude Code（终端智能体）搭配 Opus 5.5 做多文件重构，日常功能开发搭配 Cursor。智能体产出的每次变更都经过一位人工审查者的 PR。

**做对了什么：**
- 实现结账功能的时间减少 40%
- 智能体处理了样板代码、测试生成与 API 接线
- 迁移期间零生产事故
- 每次智能体会话都记录在审计线索中

**做错了什么：**
- 初期的智能体会话产生了过大的 PR（20 多个文件），难以审查
- 团队不得不在项目中途采用"只做小 PR"的规则

**学到的经验：**
- 把 IDE 助手（Cursor）与终端智能体（Claude Code）搭配使用——这是 2026 年的制胜模式
- 把智能体工作拆成小而可审查的 PR（一个 PR 一个功能）
- 保留智能体审计日志，用于合规与调试

**结果：** 迁移提前 6 周完成，测试全覆盖，零事故。

## ❌ 失败故事：未经审查的预订系统

**项目：** 一家小企业的预约预订系统。

**AI 如何使用：** 店主让智能体构建了整个系统，未经审查就接受了所有变更，并立即部署。

**出了什么问题：**
- 预订系统接受了冲突的预约（时间段被重复预订）
- 缺少输入验证，允许无效的日期与时间
- 没有身份验证——任何人都能查看或取消任何预约
- 客户投诉时，店主无法解释或修复这些 Bug

**根本原因：** 纯粹的氛围编程——凭"感觉"接受智能体产出，不阅读、不测试、不审查。

**学到的经验：**
- 未经人工审查与测试，绝不要部署 AI 生成的代码
- 身份验证与验证不是可选项——要明确指定它们
- 如果你无法解释某个功能如何工作，就不要交付它

**结果：** 系统下线，在专业开发者、测试与安全审查的参与下重建。

## ❌ 失败故事：凭据经智能体上下文泄露

**项目：** 一个连接生产数据库的内部仪表盘。

**AI 如何使用：** 一位开发者把数据库连接字符串（含凭据）粘贴进智能体提示词，以"帮助智能体理解模式"。

**出了什么问题：**
- 该凭据被发送到模型供应商的服务器并被记录
- 同一次智能体会话对仓库有写权限
- 该凭据后来被意外提交进了智能体生成的配置中

**根本原因：** 把智能体提示词当作私密的，而实际上它们不是——并且在没有密钥卫生措施的情况下给了智能体写权限。

**学到的经验：**
- 绝不要把密钥、API 密钥或凭据粘贴进智能体上下文
- 使用密钥管理器，引用密钥名称而非值
- 轮换任何可能暴露给智能体的凭据

**结果：** 数据库凭据已轮换，仓库已扫描密钥，智能体访问权限被撤销并重新限定为只读。

## ❌ 失败故事：AI 糟粕积累

**项目：** 一个客户支持门户，6 个月持续用 AI 生成。

**AI 如何使用：** 团队为每个新功能都提示智能体，从不重构，也从不为生成的代码写测试。

**出了什么问题：**
- 60% 的代码库是略有差异的复制粘贴代码块
- 重构跌到不足变更代码行的 5%（GitClear 模式）
- 随着糟粕越积越多，Bug 随时间增加
- 新开发者入职要花数周，因为没人理解这个系统

**根本原因：** 只优化生成速度，忽视可维护性。

**学到的经验：**
- 积极重构 AI 产出——把它当作初稿
- 任何生成的代码合并前都要求有测试
- 为每个 AI 组件预留维护时间（生成时间的 2–3 倍）

**结果：** 团队暂停功能开发 4 周，进行重构、补充测试并建立审查标准。

## 🔄 各故事的共同模式

| 模式 | 成功故事 | 失败故事 |
|---------|-----------------|-----------------|
| 人工审查 | 每次变更都审查 | 没有或极少 |
| 编写测试 | 是 | 否 |
| 安全扫描 | 是 | 否 |
| 能解释代码 | 是 | 否 |
| 小 PR | 是 | 大而无法审查的 diff |
| 密钥卫生 | 是 | 提示词中有凭据 |
| 已预留维护预算 | 是 | 否 |

**明确的信号：** 审查、测试并理解所交付内容的团队会成功。凭感觉接受产出的团队会失败。

## 🤝 如何投稿你自己的案例研究

本手册由社区驱动。我们欢迎任何用 AI 构建过软件的人投稿匿名的案例研究——个人开发者、专业团队、初创公司与企业。

**投稿方式：**

1. Fork 本仓库
2. 在 `27-case-studies/contributions/your-story.md` 创建文件
3. 使用下面的模板
4. 提交 Pull Request 并打上 `case-study` 标签

故事在合并前会经过质量审查与匿名化处理（删除公司名称、URL 与凭据）。

## 📋 案例研究模板

```markdown
# Case Study: [Project Name]

## The Project
One sentence describing what was built.

## How AI Was Used
Which tools, models, and agents were used, and for what tasks.

## What Went Right
- Bullet points of successes

## What Went Wrong
- Bullet points of failures, bugs, or incidents

## Root Cause
Why things went wrong (e.g., no review, missing tests, credentials in prompts)

## Lessons Learned
Actionable takeaways for other builders

## Outcome
Current status of the project

## Anonymization
Confirm no real company names, URLs, or credentials are included
```

## ✅ 实践清单

在交付下一个 AI 构建的项目之前：

- [ ] 智能体产出的每次变更都有人工审查者
- [ ] 所有关键功能都有测试
- [ ] 代码库已通过安全扫描
- [ ] 智能体上下文中没有密钥或凭据
- [ ] 你能解释核心功能如何工作
- [ ] 智能体工作在功能分支上，而非直接在 main 上
- [ ] 回滚方案已测试（一条命令即可回滚）
- [ ] 维护负责人已指定

---

## 🔑 关键要点

- **审查、测试并理解**——否则不要交付
- **成功模式**是可复现的：小 PR、测试先行、安全扫描、密钥卫生
- **失败模式**同样可复现：未经审查的产出、提示词中的凭据、没有维护预算
- **社区案例研究**是我们共同更快学习的方式——投稿你自己的案例
