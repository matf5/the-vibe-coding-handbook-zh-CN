## 🎯 为什么合规自动化现在重要

人类写代码时，合规证据是人工收集的：截图、电子表格、审计访谈。当智能体以机器速度生成代码时，人工证据收集跟不上。你需要持续运行的自动化证据收集。

**合规缺口：** 智能体产出代码的速度快于审计员评审的速度。自动化证据收集能弥合这一缺口。

## 📜 与 AI 生成代码相关的合规框架

| 框架 | 覆盖范围 | 与 AI 生成代码的相关性 |
|-----------|---------------|-------------------------------|
| **SOC 2 Type II** | 安全、可用性、保密性、处理完整性 | 智能体行为的变更管理、访问控制、审计追踪 |
| **ISO 27001** | 信息安全管理 | 风险评估、资产清单，包括 AI 模型和智能体 |
| **GDPR / CCPA** | 数据隐私 | AI 不得处理或泄露个人数据；解释权 |
| **HIPAA** | 医疗数据保护 | 智能体绝不能在未加密的情况下看到 PHI；审计所有访问 |
| **PCI DSS** | 支付卡数据 | AI 生成的支付代码必须经过评审和测试 |
| **EU AI Act** | AI 系统监管 | 披露 AI 使用情况；记录高风险系统；人工监督 |

## 📊 证据收集自动化

自动化证据收集，让审计员可以按需拉取报告。

### 要自动化的证据类型

| 证据 | 如何自动收集 |
|----------|------------------------------|
| **变更管理** | Git 提交历史、PR 评审、审批日志 |
| **访问控制** | IAM 策略、智能体权限、MCP 服务器配置 |
| **安全扫描** | 每个 PR 的 SAST/DAST 结果 |
| **故障响应** | 故障工单、事后复盘、解决时间 |
| **智能体审计日志** | 会话日志、所用模型、触及的文件、审批 |
| **培训记录** | 员工安全培训完成情况 |
| **供应商评估** | 第三方 AI 提供商安全评审 |

### 示例：自动化证据流水线

```yaml
# GitHub Actions: collect compliance evidence on every PR
name: Compliance Evidence
on:
  pull_request:
    types: [closed]
jobs:
  collect-evidence:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run security scan
        run: |
          npm run security:scan
          npm test -- --coverage
      - name: Upload evidence
        run: |
          # Store scan results, test coverage, PR approvals
          # in compliance evidence store (S3, GCS, etc.)
```

## 🇪🇺 AI 构建软件的 AI Act 合规

EU AI Act（2024/2025）按风险等级监管 AI 系统。用 AI 辅助构建的软件可能落入其适用范围。

### 风险类别

| 类别 | 示例 | 要求 |
|----------|----------|--------------|
| **不可接受** | 社会评分、操纵性 AI | 禁止 |
| **高风险** | 生物识别、关键基础设施、就业工具 | 合格评定、人工监督、文档记录 |
| **有限风险** | 聊天机器人、深度伪造 | 透明度：披露 AI 使用情况 |
| **最小风险** | 垃圾邮件过滤器、电子游戏 | 无具体要求 |

### 如果你的 AI 构建应用属于高风险

- **上市前进行合格评定**
- **实施人工监督**——人类可以推翻 AI 的决策
- **维护技术文档**——训练数据、模型信息、性能
- **实施数据治理**——训练数据质量、偏见监控
- **在欧盟数据库中注册**（针对某些高风险系统）

### 披露要求（有限风险）

如果你的应用使用 AI 生成内容或与用户交互：
- **向用户清楚披露 AI 的使用**
- **说明**何时由 AI 而非人类做决策

## 🛡️ 面向智能体工作流的 SOC 2 自动化

SOC 2 要求提供一段时间内的安全控制证据。智能体工作流使这一点变得复杂，因为智能体会自主行动。

### 要自动化的控制措施

| SOC 2 标准 | 自动化方法 |
|-----------------|--------------------|
| **CC6.1 逻辑访问** | IAM 策略、智能体最小权限、密钥扫描 |
| **CC6.6 逻辑访问监控** | 智能体审计日志、会话记录、异常访问告警 |
| **CC7.1 变更管理** | PR 评审、仅限已批准的智能体、部署审批 |
| **CC7.2 变更监控** | 部署告警、回滚跟踪、故障关联 |
| **CC8.1 变更管理（供应商）** | AI 提供商评估、MCP 服务器审查 |

### 自动化证据示例

```
Evidence: Agent access log
- Source: Claude Code / Codex audit logs
- Frequency: Continuous
- Retention: 1 year
- Fields: session_id, agent, model, files_touched, commands_run, approvals, timestamp
```

## 🔒 AI 构建系统的 GDPR / CCPA

处理个人数据的 AI 生成代码必须遵守隐私法规。

### AI 构建系统的要求

| 要求 | 实现方式 |
|-------------|---------------|
| **数据最小化** | 智能体只处理任务所需的数据 |
| **目的限制** | 不把数据用于原始目的之外的用途 |
| **访问权** | 用户可以看到 AI 处理了哪些与自己有关的数据 |
| **删除权** | 应要求删除用户数据，包括智能体上下文中的数据 |
| **解释权** | 解释影响用户的 AI 生成决策 |
| **设计隐私** | 智能体生成代码之前先评审隐私 |

### 智能体专属隐私控制

- **绝不把 PII 发送到智能体上下文**——提示前先剥离或假名化
- **记录 PII 访问**——审计智能体每次接触个人数据的行为
- **数据保留**——任务完成后删除智能体会话上下文
- **跨境传输**——确保智能体提供商遵守数据传输规则

## 🏥 AI 生成代码的 HIPAA 与 PCI DSS

### HIPAA（医疗）

| 要求 | 智能体专属控制 |
|-------------|-----------------------|
| **访问控制** | 智能体绝不能在未加密的情况下看到 PHI；仅限紧急访问 |
| **审计控制** | 记录智能体每次访问 PHI 的行为；保留 6 年 |
| **完整性** | 验证 AI 生成的医疗代码不会篡改 PHI |
| **传输安全** | 加密智能体上下文和传输中的 PHI |

### PCI DSS（支付卡）

| 要求 | 智能体专属控制 |
|-------------|-----------------------|
| **保护持卡人数据** | 绝不把卡号发送到智能体上下文 |
| **漏洞管理** | 部署前扫描 AI 生成的支付代码 |
| **访问限制** | 智能体需要最小权限；默认无权访问卡数据 |
| **监控** | 监控智能体生成的支付代码是否存在异常 |

**原则：** 如果智能体接触受监管的数据，把该智能体会话视为需要完整审计日志的特权访问事件。

## 📝 审计追踪与智能体日志

### 智能体审计日志结构

```
{
  "session_id": "agent-sess-12345",
  "agent": "claude-code",
  "model": "claude-opus-5-5",
  "started_at": "2026-11-05T10:00:00Z",
  "ended_at": "2026-11-05T10:45:00Z",
  "user_id": "dev-67890",
  "repository": "my-org/my-app",
  "branch": "feature/settings-page",
  "files_touched": [
    "src/auth/middleware.ts",
    "src/auth/routes.ts"
  ],
  "commands_run": ["npm test", "git commit"],
  "approvals": [
    {"approver": "alice", "action": "deploy", "timestamp": "..."}
  ],
  "tokens_used": 45000,
  "cost_usd": 1.80,
  "security_scan_passed": true,
  "tests_passed": true
}
```

### 保留期限要求

| 框架 | 保留期限 |
|-----------|-----------------|
| SOC 2 | 至少 1 年 |
| HIPAA | 6 年 |
| PCI DSS | 1 年（日志），部分更长 |
| GDPR | 按目的所需保留；应要求删除 |
| EU AI Act | 高风险系统 10 年 |

### 日志存储

- **不可变存储**——WORM（一次写入、多次读取）或仅追加存储
- **防篡改**——哈希链或数字签名
- **可搜索**——审计员需要按智能体、用户、文件、日期查询
- **静态加密**——尤其当日志包含 PII 或 PHI 时

## 🔑 要点总结

- **合规适用于 AI 生成的代码**——而且往往更严格
- **自动化证据收集**——人工流程跟不上智能体的速度
- **AI Act 要求披露与文档记录**——了解你的风险类别
- **智能体审计日志是你的合规线索**——记录会话、模型、文件、审批
- **绝不把受监管数据（PII、PHI、卡数据）发送给智能体**——把智能体访问视为特权访问
- **保留期限很重要**——按框架要求保留日志（1–10 年）
